# 测试版原生帧率菜单：新增 120 档

本补丁在游戏自带帧率选项中追加第五项 `120`，不再使用悬浮窗。前四项保留原来的顺序、文字编号和设置行为。它选择的是引擎已有的 120 FPS 渲染上限，不写固定模拟帧率、不替换原有 60 档，也不保证所有手机能达到 120 FPS。

当前证据包括原库静态分析和 ARM64 指令执行测试。尚未在手机上确认原生菜单最终排版、屏幕刷新率调度、持续帧率、耗电和温度，也没有把主机执行测试写成实机验收。

## 已确认的原生路径

原库来自 `release/v1.1.1/efootxi-1.1.1.apk` 内的 `lib/arm64-v8a/libUE4.so`，长度 161,937,720 字节，SHA-256：

`2cea0c85344d7d7f295aea1c2353621f02db78dbccd888a0a21a0508ac330659`

以下均为原 ELF VA；共享 Ghidra 工程显示地址须加 `0x100000`。本库 `.text` 的文件偏移为 VA 减 `0x4000`，只读数据表地址则直接对应文件偏移。

| 位置 | 静态证据 |
| --- | --- |
| `0x40c3258 → 0x36e9900 → 0x748a094` | `GetFrameRateStrList`，把原生 `std::vector<int32>` 复制到 UE 数组；元素是文字编号，并非 `FString` 或 `FText`。 |
| `0x748a094..0x748a574` | 原列表构造函数，长度 1,248 字节，固定追加四项 `0x4710169`、`0x471016a`、`0x4710254`、`0x4710253`。 |
| `0x40c3224 → 0x36e99dc → 0x748a574` | `GetFrameRateIndex`，读取配置对象 `+0x1955` 的字节。 |
| `0x40c317c → 0x36e99fc → 0x748a594` | `SetFrameRate`，保存枚举，并调用原来的渲染上限设置函数。 |
| `0x2f4bf38` | 原生上限设置，保留低档位 2/3 映射至原有 1 的行为；写入全局 `0x9baec18`。 |
| `0xc7e530` | 现有帧率表：`60,30,20,15,40,120,144,160,165,180,200,240,360,-2`。因此菜单新增索引 4 必须映射成引擎枚举 5。 |
| `0x6963e14` | 读取枚举并查表生成 `t.MaxFPS %u`。原后台低帧率逻辑继续保留。 |
| `0x810895c..0x8108968` | 已有配置恢复代码直接把保存的帧率枚举交给 `0x2f4bf38`，没有在此处将 5 限制回前四项。 |
| `0x3a555b0` | `GetString(int32)` 的 12 字节入口，通过 ARM64 `x8` 返回原生 `FString`。 |
| `0x81f36b0` | 另一条文字表查询路径，以编号返回字符串指针。 |

完整 `.text` 直接分支扫描显示，原列表函数只有 `0x36e993c` 一次外部入口调用，没有外部跳入其内部的直接分支；解析的 Android APS2 相对重定位中也没有指向该函数内部的地址。帧率读写辅助函数各自只有上述菜单包装函数的一个直接调用，没有相关重定位指针。以上是静态覆盖范围，不把间接运行行为误写为已观测事实。

没有从包资源中确认四个原文字编号的最终各语言显示文本，因此没有凭推测改写它们，也没有为了补第五项盲目修改加密 pak 索引。

## 补丁范围

`tools/patch_native_fps_ui.py` 提供 `patches(source: bytes) -> list[dict]`，返回 `{name, offset, before, after}`。每段等长，先校验完整输入 SHA，再校验各段原字节摘要，供统一构建脚本与技能补丁合并。不会在模块内写入或整体替换库文件。

1. 在原列表函数的前 `0x300` 字节内，用短循环保留已有内容并追加原四项及新第五项。继续成对使用原生分配与释放函数，结果仍是同一种三指针 vector。
2. 菜单读取时，仅将已保存的引擎枚举 5 显示为索引 4。
3. 菜单设置时，仅将新增索引 4 转成枚举 5；其余输入继续执行原设置流程。
4. 专用文字编号 `0x7fff0120` 在原库字节中未出现。`FString` 路径仅对它构造包含终止符的原生 `120` 字符串，内存由原生 FString 分配函数管理；其他编号继续执行原来的入口。
5. 底层文字表路径也只对同一专用编号返回只读的 `120`；其他编号重放原第一条指令后返回原函数继续执行。这避免不同原生控件采用不同文字查询路径时缺标签。

列表构造及小辅助片段都位于 `0x748a094..0x748a394`。另外四处仅各改一条 ARM64 分支：`0x748a588`、`0x748a5a0`、`0x3a555b0`、`0x81f36b0`。未改变 ELF 段大小、加载权限、重定位、帧率表、比赛参数、固定模拟时钟、原 DEX 或 pak。

技能选择补丁位于另一函数 `0x7baf758`，两者不共用空间。构建端仍须执行全范围不重叠检查。

## 栈和展开边界

列表主路径保留原函数的 `0x40` 栈帧及 `x19..x23` 保存位置，新循环结束后跳至原 `0x748a448` 的 epilogue。原 FDE 位于 `0x24fe518`，入口第 20 字节后为 `FP+64`，主循环及原 epilogue 继续符合该描述。

新辅助片段正常执行保持 ARM64 调用约定；其中需要调用原生内存分配函数的片段采用同一栈布局。执行测试验证 `SP` 与 `x19..x29` 全部恢复。但各辅助片段进入/退出临时栈帧的短窗口没有新增独立展开记录，若恰在这些指令被异步采样或崩溃，原展开表不保证生成准确回溯。未修改整个 `.eh_frame` 来掩盖这一已知调试限制。

## 已执行的验证

运行：

```powershell
python -m unittest discover -s tests -p test_native_fps_ui.py -v
```

8 项测试通过。测试读取真实发布 APK 的库，使用 Unicorn 执行原/新 ARM64 代码；只在内存分配、配置对象获取和不相关的旧文字查询边界接入替身，没有运行 Android 游戏。

- 空列表、已有条目、不同预留容量：原函数结果保持原四项，新函数只追加 `120` 的编号，已有条目不丢失。
- 原四个菜单选择及其余枚举逐项对照，只有新增索引 4 保存为 5。
- 已保存的 256 种字节值中，仅 5 显示为 4。
- 原配置恢复指令能把 5 交回原渲染上限函数；原帧率表第 5 项仍为 120，第 0 项仍为 60。
- 新文字是具有正确长度、容量、终止符和原生分配所有权的 UTF-16 `FString`。
- 原文字编号全部继续经过原入口；底层字符串表的新编号返回 `120`，旧编号保留原参数和 prologue。
- 保存寄存器与栈均恢复；每段原字节摘要、完整输入摘要、等长和互不重叠检查通过。
- 用 Keystone 重汇编模块内的可读汇编，逐段比较实际嵌入机器码。

另检查了读取帧率配置的 `0x7abf8f8`：它对前几个档位取得阈值，其唯一直接调用方 `0x6a8e060` 将结果用于 `0x82af998` 的比较/计数流程；枚举 5 沿原有默认路径跳过这项计数。该路径没有在已检查指令中覆盖帧率枚举或设置固定模拟步长，本补丁保留它。其完整业务含义仍属静态推断边界。

## 手机验收范围

1. 打开游戏自带帧率设置，确认原四项完整保留，并可滚动或选择新增的 `120`，文字不空白、不遮挡。
2. 分别选择旧档位与 120，离开设置后重新进入，确认选中项准确。
3. 选择 120 后正常退出、强退重开，确认设置保留；资源下载和存档流程不受影响。
4. 在菜单、普通本地比赛、我的联赛及 AI 组别检查帧率和比赛时间流速；确认中场、换人、回放及比赛结束后设置未重置。
5. 在高刷与普通屏幕设备上检查实际渲染帧率、系统刷新率、电量和温度。实际120能力取决于设备与系统调度，这项测试尚未完成。
