# 个人比赛统计接入状态

## test.2：已接入，待手机完整比赛验收

2026-10-17，当前 11.1.1 核心的原生结算序列化已定位，具体证据与限制见 [原生协议证据](match-statistics-native-schema.md)。test.2 将正常完赛的出场、进球、助攻接入 SQLite，覆盖我的联赛、AI 组别和本地服务创建的普通人机比赛。

1. 开赛保存实际送入比赛的阵容，以球员持有实例 `(id,serial)` 区分同卡多份。
2. 读取 `match_result.myteam_player_list` 的参与数据；接受 `YES/NO` 标记，上场时间大于零、首发或已登场满足任一条件即计一次出场。未登场替补不计。
3. 根级 `goal_player_list` / `assist_player_list` 每个元素对应一次事件。相同实例重复出现按多次事件计数，空事件列表允许省略。对手列表不混入，点球大战比分不补入。
4. 三项累计与比赛结果在同一事务提交；以比赛 ID 和规范化个人增量防重。重复请求不重复增加，冲突的同场个人增量拒绝覆盖。
5. 数据缺失或未识别时仅个人记录进入 pending，不因此改写比赛胜负。后续同场完整请求可以补记一次，不重复领取比赛积分或奖励。
6. 主动弃赛不计个人统计。没有保存个人数据的旧版比赛不能凭空追补；不按球队比分猜测进球和助攻归属。
7. 关库重开后，详情与登录球员数据读取已有累计。没有构造未经确认的即时刷新协议；赛后原生页面缓存是否及时刷新仍需手机核对。

主机测试覆盖三模式、主客场、同卡副本、替补、重复事件、缺字段后补记、数据库重开及故障回滚。标记的完整引擎取值、各模式是否总是发送这些数据，以及零分钟登场边界仍需实机确认；静态字段恢复不等于手机验收。

## 下一步接入条件

取得正常完整比赛的结算字段，并与已知进球、助攻和换人情况对照。首先确认每条事件代表一次发生还是累计值，`id` 指卡片定义、持有实例还是场上索引，是否携带 `serial`，以及首发、上场替补、未上场替补的表示方式。再接入现有事务接口，并覆盖重复上报、重启、同卡副本、乌龙球、无助攻进球和中途退出。

该本地累计功能本身不依赖官方服务器。当前缺口是可靠的比赛数据适配与手机验证，不能仅凭总比分给球员分配统计。
