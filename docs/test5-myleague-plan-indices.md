# test.5：我的联赛开赛名单与阵型引用

本轮只修改测试版。用户已确认 AI 组别有效性和个人统计正常，本功能不改 AI 结算、球员参数、比赛风格或技能效果。

## 已确认的问题

原生 START 的 MessagePack 序列化函数 `0x77cd1e8` 会保留 `(id=0, serial=0)` 空位置。test.4 在请求名单非空时直接解析所有项目，空位置可能进入“未知球员”拒绝路径；这发生在记录“已确认开赛”之前。手机反馈停留在 PREPARED，与该路径吻合，但未取得该手机的完整请求体，不能据此声称排除了全部入场故障。

过滤空位置后也必须处理阵型：例如原 23 个位置中的一个替补为空，压缩名单只剩 22 人，原计划仍引用位置 22，就会引用不存在的条目。修复不能只跳过空球员。

## 当前处理

`myleague_plan.gameplan_for_entries` 在确认开赛和写入存档之前，根据保存阵容中的球员身份与本次 START 返回名单建立位置映射：

- 保留全部实际球员及请求中的实际球员顺序。
- 调整 `match_plan_settings.order`、队长、定位球主罚、定位球前插和教练联动的成员引用。
- 首发必须对应 11 名不同且实际存在的球员；缺少必需首发时明确拒绝，避免自动用另一个替补冒充该位置。
- 空替补和已删除的可选引用使用原生未设置值 `255`。原本就是 `255` 的队长、教练联动引用原样保留，包括捕获中 `is_link_on='YES'` 但两个成员仍为 `255` 的状态。
- 保留球员参数、位置坐标、比赛风格和战术数值。相同的成员位置映射不会修改普通阵型内容。
- 阵型和球员存档本体不会被该转换重写，只生成本次开赛的私有副本。

`team_tactics.data` 的目标语义尚未得到充分原生证据，不作猜测。只有当本次名单确实改变成员位置、且原计划启用了非零 `team_tactics.value_id` 时，明确返回 `unverified_match_tactics_reindex`；相同位置映射下保留原指令。此处仍是小范围限制，需要后续带具体个人指令的手机反馈或更深的原生目标映射证据。

## 原生消费证据

目标库 SHA-256：`2cea0c85344d7d7f295aea1c2353621f02db78dbccd888a0a21a0508ac330659`。地址均为原始 ELF VA；既有 Ghidra 工程显示地址另加 `0x100000`。

在现有 REA 工作流下复用只读 Ghidra 工程，不运行 Android 应用、不保存分析数据库。Android ARM64 ELF 不在当前 Windows REA 原生 provider 的支持范围内，因此沿用既有离线 headless 分析。

1. 反射表的 `IsCaptain` thunk `0x3fea87c` 调用业务函数 `0x330c770`。对球场位置 0～10，该函数先经 `0x70948a4 → 0x6a52448` 读取 `order[pitch_position]`，再与设置对象 `+0x31` 的队长成员值比较。队长保存的是成员引用，不是球场位置。
2. `HasLink` thunk `0x3fe59c4` 调用业务函数 `0x3313320`。该函数读取联动的两个成员值，经过 `0x70948ac → 0x32d5da0` 反查其在 `order` 中的位置后返回给 UI。联动成员同样不是球场位置。
3. `0x6a52448` 直接读取最多 40 项的 `order` 字节；`0x32d5da0` 反查其中与成员值相等的项目。它们不是根据字段名猜测出的辅助函数。

`build/myleague-test5/execute_plan_consumers.py` 执行了当前原版 ARM64 的上述两个 UI 消费函数和两个顺序转换函数。采用非恒等排列 `order=[4,2,0,3,1,...]`：队长成员 4 对应球场位置 0；联动成员 `(5,1)` 对应 UI 返回位置 `(4,5)`。将球员容器反序并同时重映射引用后，11 个球场位置的队长判断、联动返回位置全部保持一致。

这个验证只替换单例／模型定位、租借模式开关和无效联动刷新为主机辅助；关键 UI 判断及顺序转换运行的是原 ARM64 指令。结果记录为 `build/myleague-test5/executed-plan-consumers.json`。它不是手机运行或完整原生网络解析的验证。
