## 手机反馈确定了什么

用户提供的 test.4 本地反馈页中，AI 组别一场 6:0 返回 WIN / NORMAL_END / NOERR，个人统计已保存，收到 23 名球员、6 条进球事件和 5 条助攻事件。用户确认 AI 有效性已经解决；本轮不调整已经验证的胜平负分类。

我的联赛停在 PREPARED，尚无成功 START 记录；后面有模式未确认的拒绝事件。旧通知页把不符合代码格式的异常句子隐藏为「未识别」，因此这张图本身不能证明手机具体传入了哪一项身份。

原生 ARM64 START 序列化函数 `0x77cd1e8` 的实际指令执行证明：空数组会保留，`id=0,serial=0` 空槽也会原样发送。test.4 对非空数组直接执行球员查找，在正式身份策略启用时把 0/0 当成未知球员，拒绝后不记录 START。这是确定缺陷，且时序与手机记录吻合；手机原请求并未被抓取，不能因此宣称已证明唯一根因。

原生 PREPARE、START 回复、赛季排名、场次比分、比赛历史和射手榜行结构也已核对。Ghidra 只读与 ARM64 合同执行证据在本地 `build/myleague-test5/`，使用的原库 SHA-256 为 `2cea0c85344d7d7f295aea1c2353621f02db78dbccd888a0a21a0508ac330659`。

队长、教练联动的原生业务函数已通过非顺序阵容的实际 ARM64 指令执行验证，证明它们引用球员容器成员，并核对重映射后的场上归属保持不变。允许原生 `YES + 255` 未指定组合。具体证据及尚未确认的主动个人战术重排限制见 [阵型索引](test5-myleague-plan-indices.md)。

## 本轮范围

1. 正确认识 START 的精确 0/0 空槽；非空身份仍验证所属与重复，不补入任意其他球员。
2. 空名单恢复本赛季保存计划；过滤空位时核对计划索引，避免造成新的首发或阵型错误。
3. 拒绝记录保留比赛模式、开赛步骤与安全错误代码，通知页不暴露任意异常文字。
4. 未成功开赛就提交结果仍拒绝，不推进赛程、不增奖励，不把菜单上的 0:0 占位当作已踢完。
5. 我的联赛当前轮 CPU 比分预览与正式提交共用同一份确定性结果。读取页面不会修改积分或战绩。
6. 射手榜、助攻榜只使用本赛季统计，同时包含我方、实际交手的 AI 球员与其他模拟 AI 场次的球员；细节与覆盖缺口见 [赛季榜单](test5-season-rankings.md)。
7. 同场重复请求、重启、换赛季隔离和缺数据后补记均做回归；不凭空恢复旧版未记录的比赛。
