# 我的联赛保存阵容与开赛协议

`CMD_SET_MYCLUB_SPECIAL_DREAM_SQUAD_INFO` 保存本赛季的球员顺序、教练与战术。`CMD_START_GAME` 读取这一份已保存计划；旧存档尚未保存特殊阵容时，使用普通主阵容。不能从请求名单读取球员、再从另一份保存计划读取阵型索引。

独立参考包 Ziru 的 `handleZiruMyLeagueStartGameV71` 从持久化特殊阵容读取上述内容，START 请求仅用于 rqid、game_id。其正常对象回复经 MessagePack、gzip 与加密输出，未找到另一个在输出时重写开赛阵容的处理器。REA 提取和调用链证据保留于本地 `build/myleague-test6-reference/`。新 73 参考包与本项目属于相近 Python 实现，不能把两者的相同代码当作独立真机成功证据。

本项目保留当前 owned 存档生成的 147 项比赛参数，包括培养、技能、惯用脚、逆足和风格。START 的 `player_list_home` 只作缓存诊断：字段存在时仍须为数组，但其中的顺序、重复项、旧引用或空项均不能选择、补充或复活球员。原生 START 序列化器没有 `squad_id`；它不能覆盖已保存特殊计划。主客场来自已准备赛程；请求 side 只在 HOME/AWAY 时作为诊断记录，不决定球员来源。

保存源本身保持严格核对：身份必须是正整数 id/serial，或精确的 0/0 空位；未知和重复 owned 实例拒绝开赛。确有解约记录的旧特殊阵容引用按空位处理，不要求额外重新保存。阵型验证仍拒绝缺少首发，允许未使用替补为空，并按身份同步索引；不会从其他 owned 卡随机补人。错误不推进赛程，不增加积分或个人统计。

旧特殊阵容未被 identity migration 改写时，仅使用存档内明确记录的 owned identity alias 转为同一份 canonical 卡实例；展示与开赛先做相同转换，再检查解约和所有权。不按卡 ID 猜另一份实例，也不把未知 serial 0 当作别名。该读取转换不改写原特殊阵容记录。

`test_myleague_authoritative_start.py` 使用真实 23 人阵型，先以旧请求优先边界重现缓存未知引用被拒绝，再验证同一保存计划在新流程下成功返回开赛数据。另覆盖冲突普通阵容、保存源损坏、重复卡、解约替补和解约首发。`test_player_match_parameters.py` 对实际 APK 存档的全部 147 项参数逐项回归，AI 与普通比赛继续使用各自原有名单规则。

这些测试验证本地服务合同与数据一致性，成功返回开赛数据不等于已在手机进入球场，也不能据此宣布 test.5 的手机转圈故障已经解决。被动步骤记录用于区分请求未到达、处理异常、拒绝响应，以及开赛响应后发生的失败。

当前原生业务辅助函数 `0x7bcb26c` 只更新缓存中已有的匹配球员，未证明可以插入新的球员 ID。缓存未知引用的测试因此只证明服务端不再把缓存当作开赛阵容权威，不能证明客户端会修复任意陈旧缓存，更不能把这个反例直接当作本次手机故障的唯一原因。
