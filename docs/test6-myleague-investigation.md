# test.6 我的联赛再次对照与修正

2026-10-17。用户确认 test.5 仍有此前同样的未入场、未知网络错误、空排名／0:0 页面。本轮只修改测试版，生成本地包，不上传 GitHub、不改正式版。

## 开赛阵容采用同一份已保存计划

test.5 的 START 会优先使用请求中的缓存名单，同时从保存记录恢复战术和教练。缓存与保存计划不一致时，会发生拒绝或重新对齐；这一流程与独立 Ziru 参考包不同。Ziru 的 `handleZiruMyLeagueStart` 不采用请求两边的球员数组，而是恢复保存的专用名单、教练、战术。真实原生 START 不产生 `squad_id` 字段，联赛阵容修改则通过 SaveSpecial 保存。

test.6 将我的联赛 START 统一为：存在本赛季专用计划时使用该计划的名单、教练、战术，否则使用保存的当前主计划。请求中的缓存名单不再覆盖其中一部分，额外的 `squad_id` 不再改变选择；比赛主客场取当前赛程。缓存数组仍须是合法容器，但其中过期引用不再阻止有效保存计划开赛。

实际保存的计划仍严格检查球员实例存在、唯一及身份完整性，只允许精确的 0/0 空槽；已有解约记录的替补转换为空位，首发不齐不会随机补入其他卡。旧特殊计划中存在明确迁移映射的球员编号，展示与开赛同时转换为同一实例，不猜测未知编号。沿用战术位置检查、队长／定位球／心有灵犀引用转换，完整读取现有实例的培养、技能、风格和逆足等参数。AI 组别不使用这条改动。

这是参考包支持的流程统一，可构造 test.5 旧行为拒绝、新行为成功的缓存过期对照；尚未取得本次手机上的完整请求和精确拒绝原因，不能据此断定它就是手机转圈的唯一根因。原生已返回开赛数据也不代表游戏已经进入球场。

原生辅助函数 `0x7bcb26c` 仅更新缓存中已有的匹配卡 ID，不能据此宣称开赛回复能重建任意陈旧的客户端名单。旧缓存反例只证明服务端不再混用两个来源，不能替代手机运行验证。完整保存合同见 [开赛阵容](myleague-start-contract.md)。

## 准备状态仅作旧存档防护

`own_special` 改为在实际返回已准备的联赛计划时回 `initial_settings=YES`。原生进入转换函数 `0x7655704` 在 NO 时忽略本次专用计划、查找普通主计划；主计划不存在会提前返回。Ziru 的 common-state 方法亦明确设 YES。

实际执行当前原库 ARM64 指令验证了上述三个分支，并发现另两处 NO 时自动重建阵容的消费者。但继续追到真实 SaveSpecial 生产函数 `0x7918354` → `0x7655640` 后，确认它无论输入准备位如何都会发送 YES。因此，这项修正仅覆盖旧异常保存状态，不能作为正常手机流程的已证根因。执行材料在 `build/myleague-test6/execute_special_readiness.py`、`execute_special_producer.py` 及对应 JSON。外部查询、转换和 libc 是声明的宿主接缝，不是手机整场测试。

## 已核对并排除的猜测

1. 原生真实 START 生产函数 `0x77c7aac` 根据受控一方选择玩家阵容，一直写入 `player_list_home`。字段名不代表玩家必须是赛程主队，不交换主客双方数组。
2. 真实生产函数会先排除 0/0 空身份。test.5 仅执行序列化器证明它能写空槽，不能据此推断正常手机一定发送空槽。上轮空槽防御处理保留，但不再把它称为本次手机问题的已证原因。
3. 赛季进入回复的球员与教练引用格式有效；原生 `0x7652c74` 读取身份和号码，不需要在该回复塞入完整球员参数。
4. CHECK_MATCH_ENABLE 与 SEND_MATCH_TEAM_INFO 的当前捕获回复和 Ziru 分派字段一致，没有依据增加猜测接口。
5. 参考包的 `team_id=0`、球衣列表与当前不同，但尚未找到证明这些差异导致失败的条件，不凭字段差异任意改球队或制造球衣 ID。
6. 新 73 参考 APK 的网关与当前 Python 代码同源，不能把它当成独立的手机开赛成功对照。Ziru 的独立 Java 分派、进入和开赛方法另作对照。REA 原始证据与纯 Java 摘要在 `build/myleague-test6-reference/`。
7. 当前原生明确支持对手球员与教练数据为空时从内置资源恢复。已核对全部 444 支赛程球队：球队、名单、门将与关联教练均存在，不凭空改成另一套虚构对手数据。
8. 真实生产端使用 SEASON_MODE、明确的 HOME/AWAY、完整 64 位比赛 ID；名单上限 40，与当前协议一致，未发现正常生产端在这些字段上的违约。

## 球队名单全部补齐

从安装资源本身恢复 834 队、24,050 条球员所属关系，当前赛事 441 队零缺失，原先缺少的 26 队全部补齐。解析所得 CPK 与 APK 资源清单的字节数、SHA-256 完全一致；全部球员／球队外键存在，7,092 个现有位置值交叉核对零差异。详见 [球队名单与榜单](test5-season-rankings.md)。

旧赛季只补原先缺队的其他 AI 场次事件，使用已保存比分，保留已存在球队的个人记录、积分和赛程。真实对手仍必须上报实际进球和助攻，不根据比分猜球员。

补记在恢复赛季或准备比赛的现有写事务中进行，已完成赛季也在提前返回前补记；普通榜单读取保持不生成记录。新增完成赛季回归覆盖重复恢复、关库重开、其他赛季隔离、积分／比分／累计个人统计不变。

## 奇数球队联赛轮空

使用真实种子逐队开赛发现马来西亚 13 队赛程存在轮空。原处理要求每轮必须找到我方比赛，会在轮空轮次拒绝。现仅推进没有我方比赛的轮次，保存该轮其他 AI 比赛与榜单，再找到下一场实际我方比赛；不捏造我方 0:0、不增加我方出场、积分、奖励或个人统计。覆盖新赛季、中途轮空、最后一轮轮空、旧存档恢复和只读菜单。Kelantan TRW 的完整 26 轮只有 24 场我方比赛，已按此核对。

## 更完整的本机反馈

原生右上角通知新增最近八步的安全流程摘要。记录请求进入及回复完成状态，能区分没有收到开赛请求、处理时抛错、已返回数据后仍未进场。不上传，不弹窗，不记录账号、令牌、球员身份或完整请求；不提交或回滚业务事务。已有未提交业务事务时跳过日志写入，避免影响存档。

成功的 START 另比较请求缓存与回复中的卡 ID 集合及顺序，只保留共有／各自独有的数量与顺序是否相同，不存 ID 或哈希。只有完整可解析的数组才比较，旧零 serial 或其他无法确认的缓存不生成部分比较结论。日志自身的分类读取失败不阻止业务处理；错误原因只关联本次请求进入后产生的拒绝，避免串入更早失败。
