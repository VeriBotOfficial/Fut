# 我的联赛进球榜与助攻榜：test.5 接入、test.6 补齐名单

2026-10-17。本次只修改测试版；不是手机验收结论。

## 原因与显示协议

此前 `my_league.info` 每次明确返回空 `goal_ranking` 和 `assist_ranking`。球员详情的累计出场、进球与助攻另有存储，它们不是本赛季排行榜，不能直接拿终身累计填榜单。

现使用游戏已有的两张榜单，不新增悬浮窗口。当前核心 `libUE4.so` 的 SHA-256 为 `2cea0c85344d7d7f295aea1c2353621f02db78dbccd888a0a21a0508ac330659`。本地 Ghidra 对 GET_SEASON_INFO 解码器原始 VA `0x795b4e4` 的聚焦分析确认，两张榜单共用行解码器 `0x7565198`：

| 原生字段 | 类型 | 原生行偏移 |
| --- | --- | --- |
| rank | int32 | 0 |
| player_id | int64 | 8 |
| team_id | int32 | 16 |
| value | int32 | 20 |
| is_com | string，YES/NO | 24 |

行长 48 字节。当前解码器没有 serial；同卡多个持有实例仍在个人累计中分开，榜单按卡片 ID 合并。并列名次用 `1、1、3`，与包内捕获的赛季信息一致。没有找到限定只显示前 20 行的当前原生证据，因此服务端不照搬捕获样本的 20 行截断。

REA 技能用于沿用现有交付物与协议分析；本机 REA 的 Ghidra provider 不支持 ARM64 ELF，本轮继续使用已经导入的本地 Ghidra 离线只读分析，不冒称 provider 支持。详细伪代码和原始 ARM64 解码器执行材料保存在忽略提交的 `build/myleague-test5/`，包括 `7565198.strings.c`、`execute_row_decoders.py`、`executed-row-contracts.json`。生产请求事件的已确认结构见 [统计协议证据](match-statistics-native-schema.md)。

## 记录来源与持久化

1. `season_rankings.py` 使用独立赛季账本，以赛季序号、赛事和所选球队共同划分范围。比赛积分、终身个人累计、本赛季榜单在同一个 SQLite 结算事务内持久化。
2. 我方真实比赛数据沿用已验证的持有实例适配器，读取 `goal_player_list` 与 `assist_player_list`，保留重复事件；不按比分猜测谁进球。
3. 实际对手读取原生的 `opp_goal_player_list` 与 `opp_assist_player_list`。这两个列表每项是一个 int64 球员 ID，与我方 `{id,serial}` 结构不同。开赛准备时冻结对手球队及可用的内置球员名单；只接受该球队名单内的 ID，事件数量不能超过该队实际比分。
4. 对手比分大于零而进球列表缺失时，保留待补记状态；后续同场完整重试可以补记。零比零时可省略空列表。明确提供但少于总比分的进球事件仅记已知球员，不为可能的乌龙球补造射手。
5. 其他球队之间的比赛使用本地赛程原有的确定性比分模拟，另将进球与助攻分配给各自球队名单中的球员。模拟事件与该轮模拟比分一起保存一次，进球总数严格等于模拟比分，助攻数不超过进球数。这些是本地模拟赛事，不是用户实际踢过的比赛记录。
6. 当前资源的原生 Player.bin 为名单内全部 22,900 个球员提供位置，按已核对的 `parameters[0]` 编码提供模拟权重；门将不参与常规模拟进球和助攻，前锋获得较高进球权重。不把名单顺序当成阵型。只有旧环境缺少新数据文件时，才沿用注册卡位置与中性权重的兼容路径。
7. 用户所选球队的整场比赛（包括其真实对手）均排除在其他场次的模拟中，避免既模拟又从原生列表重复计数。
8. 同场同轮重试不重复累加；已接受的事件不能被另一份冲突事件覆盖。个人统计缺失和对手统计缺失可各自补记。旧赛季的迟到重试使用原先冻结的赛季上下文，不会污染新赛季。
9. 排行榜读取只汇总已持久化账本，不推进赛程、不生成未来轮次、不改积分。重启后仍从 SQLite 读取。
10. 主动弃赛不记录真实个人进球、助攻。旧版本没有冻结赛季上下文的历史比赛不能可靠地追补归属，本轮不按终身累计倒推出虚构赛季记录。

原始来源是 `D:/ef/73efootball-resources.zip` 的小成员 `Download/dt870_mobile_and.cpk`，不是网上查询的转会名单。CPK 仅 7,323,280 字节，SHA-256 为 `27472fe8f02de4346910996cdc6200940937efee22bfe6eeb1f5326644b032e8`。只读取其中的三份 pesdb 表，原始 APK、资源 ZIP 和 CPK 均未修改。

WESYS 外层数据的解包方向先对照了公开项目的[原始 WESYS 实现](https://github.com/Master-Antonio/Efootball-Mod-Studio/blob/c0778355a8153a014c8e1d9ae040f7ec55b4a350/ui/core/wesys.py)及[原始表格式实现](https://github.com/Master-Antonio/Efootball-Mod-Studio/blob/c0778355a8153a014c8e1d9ae040f7ec55b4a350/ui/core/pesdb.py)，随后用本仓库的独立、受限脚本在本地副本处理。没有执行下载的代码或游戏程序。当前三份表均通过 zlib 校验和与声明长度检查。

| 原生表 | 解包字节 | 记录数及字段 |
| --- | --- | --- |
| PlayerAssignment.bin | 577,200 | 24,050 × 24 字节；球员 u64 在 +8，球队 u32 在 +16 |

所有所属关联的球员都能在 Player.bin 找到，所有球队都能在 Team.bin 找到；每队 11–40 人、队内无重复 ID。位置字段另与现有注册卡交叉核对：**7,092 张卡的位置完全相同，差异为 0**。旧 415 队中的多份名单与当前资源有转会变化，因此新数据以同一份实际资源的原生关联为准，不把旧名单缺漏或顺序当成新表布局的依据。

完整的成员原始哈希、解包哈希、记录宽度和偏移写在新 JSON 的 `source` 字段。规范 UTF-8/LF 数据文件的 SHA-256 为 `5495d0562e290bafae0f329b6464ce9ecf3aaeeb95c76a4daa9c94afe3496f8a`。生成命令：

### 已有存档的补记边界

1. `repair_missing_fixtures` 仅查看已经保存在本赛季 `played` 中的比分，并只给旧账本 `unavailable_teams` 对应的队伍补模拟个人事件。其他队已接受的记录不重新分配；反复处理不重复累加，不创建未来比赛，不改变积分或比分。
2. 旧准备记录尚未开赛时，使用当前完整名单建立比赛上下文。旧同场真实对手统计处于待补记状态时，可按原先冻结的对手球队恢复当前原生 ID 校验列表，保留原赛季、我方实例、比赛 ID 和已接受比分；仍必须收到该场真实进球/助攻事件才会记录。
3. 没有保存真实事件的历史比赛不能仅按比分恢复具体射手或助攻者。本次不会为真实踢过的比赛猜测个人归属。
4. 原生表解析与协议测试证明数据来源及结构；手机仍需核对比赛实际进入、事件上报以及两张榜单的绘制。数据覆盖完整不等于已经在所有手机验收。

此前的只读资源核查证实两个参考 APK 内的旧 `ml_rosters.json` 完全相同，SHA-256 为 `6e32f999a29fffabb6815c7471da4170fe91e7789523c14ec2e53a5fb32ff5bf`，不能互相补齐缺队。test.5 当时只确认 CPK 内有 WESYS 包装的表，尚未解开；test.6 已完成上述本地解包与交叉验证。原始目录审计和未修改成员保留在 `build/test5-roster-coverage/`，用于核对前后结论。
